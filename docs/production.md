# Эксплуатация Saturnita Pulse

## Подготовка VPS

Production-профиль находится в compose.production.yaml. Caddy раздаёт собранные файлы React и направляет API в Go. PostgreSQL доступен только из внутренней сети Docker. На хосте нужны Docker Compose, постоянный диск, свободные 80/443 и настроенный firewall. Запишите версии образов и git revision релиза перед обновлением.

Для apex saturnita.ru и wildcard *.saturnita.ru подготовьте A-записи на адрес VPS. AAAA добавляйте только при рабочем IPv6. Сертификат apex запрашивает Caddy. Для wildcard получите сертификат DNS-01 выбранным ACME-клиентом и автоматизируйте продление. Положите полную цепочку wildcard.pem и приватный ключ wildcard.key в каталог, доступный Caddy только для чтения. После замены файлов выполните `docker compose -f compose.production.yaml exec edge caddy reload --config /etc/caddy/Caddyfile --force`. Персональные поддомены используют один wildcard. Для внешних доменов Caddy проверяет внутренний ask endpoint при выдаче сертификата. TXT и CNAME настраивает владелец домена в кабинете.

В отдельном закрытом env-файле задайте POSTGRES_PASSWORD (случайное URL-safe значение), ANALYTICS_MASTER_KEY (случайные 32+ байта), ACME_EMAIL и абсолютный WILDCARD_CERT_DIR. Храните ключ аналитики и ключи TLS отдельно от Git. MONITOR_WORKERS по умолчанию равен 10, допустимый диапазон 1–32. Каждый экземпляр backend запускает собственный пул. Доступ к исходящим TCP-соединениям ограничьте публичными 80/443 и необходимыми DNS/DB направлениями на уровне хоста. Приватные и специальные адреса дополнительно блокирует приложение.

После подготовки DNS и сертификата на VPS: `docker compose --env-file /etc/saturnita/pulse.env -f compose.production.yaml up -d --build`. Далее в примерах `dc` обозначает ту же команду Compose с теми же параметрами. Проверьте `dc ps`, /healthz и /readyz через apex, регистрацию, реальный переход через go и получение check в кабинете. Ошибки подключения или проверки видны по категории. Логи backend структурированы, body ответа внешнего сайта не сохраняется.

## Резервное копирование и восстановление

Целевой режим одного VPS: ежедневный зашифрованный off-host backup и отдельная копия env и сертификатов. При таком графике целевой RPO — 24 часа. RTO оцените по длительности пробного восстановления фактического объёма базы. Для PostgreSQL используйте custom-format dump. Пример для POSIX shell: `dc exec -T db pg_dump -U pulse -d pulse -Fc > pulse.dump`. Ограничьте доступ к архиву и проверяйте его через `pg_restore -l pulse.dump`. Хранение копий ограничьте принятой политикой приватности.

Пробное восстановление выполняйте в новой изолированной БД без запущенного worker: `createdb -U pulse pulse_restore`, затем `pg_restore --exit-on-error --no-owner -U pulse -d pulse_restore pulse.dump`. Сверьте версию schema_migrations, количество сущностей, историю проверок и вход тестового пользователя. Для восстановления сервиса остановите writers, восстановите копию в отдельный том, переключите совместимую версию приложения и проверьте readiness до открытия трафика. Старый том сохраняйте до приёмки. Перед миграцией снимайте backup. Возврат предыдущего образа допустим только при совместимой схеме, иначе используйте сохранённую копию. Down-миграции удаляют данные соответствующего этапа.

## Проверки и ограничения

| Область | Проверка |
| --- | --- |
| Права и приватность | HTTP-тесты кабинета и браузерные тесты разных владельцев проверяют доступ и сессии. Backend пишет метод, идентификатор запроса и признак ошибки. Дневные HMAC-псевдонимы хранятся в таблицах событий. |
| Сеть мониторинга | Тесты подставляют DNS и соединение, проверяют допустимые адреса, совпадение адреса подключения, пределы ответа, таймаут и поведение при 3xx. |
| Планирование и аналитика | Интеграционный тест PostgreSQL проверяет возврат просроченной аренды, отбрасывание запоздавшего результата, смену состояний, закрытие инцидента, uptime и p95. |
| Поставка | CI собирает frontend и проверяет Go с детектором гонок, OpenAPI-типы, браузерные сценарии, пробное восстановление и конфигурацию Caddy с временным сертификатом. Реальную выдачу сертификатов и доступность извне проверяют после настройки VPS. |

В CI скрипт `deploy/restore-drill.sh` проверяет восстановление текущей версии схемы, добавляет демоданные в восстановленную копию и проверяет повторный запуск. Для DNS-01 ограничьте токен DNS-провайдера изменением записей нужной зоны и передавайте его только клиенту продления. Доступ к настройкам регистратора контейнерам приложения не нужен.

Состояние Unknown означает отсутствие проверки текущей конфигурации, Degraded — первую ошибку, Down — две последовательные. После успеха инцидент закрывается. Пауза завершает открытый инцидент и сохраняет историю. Ручная проверка только ставит задание в расписание, не чаще раза в пять минут на монитор. На аккаунт допускается 50 мониторов. Для HTTP GET лимит тела 64 КиБ: страницу большего размера проверяйте HEAD, если нужен только статус. 3xx сравнивается с заданным диапазоном. Входящие redirects клиента мониторинга отключены. История checks хранится 90 дней; число проб, средняя и p95 включают завершённые ошибки и таймауты. Оценка относится к наблюдениям с этого сервера. При потере процесса после отправки запроса сеть может увидеть повтор, но фиксация результата защищена арендой и уникальностью слота.

Чтобы наполнить отдельный локальный демоаккаунт историей, создайте его через /register, затем выполните из корня в POSIX shell `docker compose exec -T db psql -U pulse -d pulse -v owner_email=demo@example.test < deploy/demo-seed.sql`. В PowerShell используйте Get-Content -Encoding UTF8 -Raw и передачу в psql через pipe с UTF-8 OutputEncoding. Скрипт добавляет демонстрационную ссылку и приостановленный монитор с подписанным демонстрационным именем. Запуск повторяем и всегда явный.
