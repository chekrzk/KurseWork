# Техническое задание: Saturnita Pulse

## 1. Общая информация

**Название:** Saturnita Pulse

**Тип:** Full-stack SaaS / Web Application

**Основной домен:** `saturnita.ru`

**Назначение:** разработать полноценную веб-платформу для сокращения и управления ссылками, сбора аналитики переходов и посещений, а также мониторинга доступности HTTP-ресурсов.

Система должна быть пригодна для реального использования, а не только для демонстрации. При этом архитектура должна оставаться понятной, без необоснованного усложнения.

### 1.1. Основные модули

1. **Link Management** — создание и управление короткими и реферальными ссылками.
2. **Link Analytics** — сбор и визуализация статистики переходов.
3. **Web Analytics** — аналитика подключённых сайтов через JavaScript-трекер.
4. **Uptime Monitoring** — мониторинг HTTP endpoints, сайтов и API.
5. **Domain Management** — управление поддоменами и пользовательскими доменами.
6. **User Dashboard** — единый интерфейс управления всеми инструментами.

### 1.2. Примеры использования

**Сценарий A — сокращение реферальной ссылки**

Пользователь добавляет исходную ссылку:

`https://example-shop.ru/product/123?ref=partner123`

Создаёт короткую:

`https://go.saturnita.ru/product`

При открытии короткого URL система фиксирует переход, проверяет ограничения и выполняет перенаправление.

Реферальные параметры должны сохраняться. Сервис не создаёт партнёрские идентификаторы за пользователя и не гарантирует атрибуцию у стороннего магазина.

**Сценарий B — персональный поддомен**

Пользователь регистрирует доступный поддомен:

`alex.saturnita.ru`

После регистрации сможет создавать:

`https://alex.saturnita.ru/promo`

`https://alex.saturnita.ru/github`

`https://alex.saturnita.ru/portfolio`

Все ссылки обслуживаются одним Go-приложением. Создавать индивидуальные DNS-записи для каждого поддомена не требуется.

**Сценарий C — аналитика сайта**

Владелец сайта подключает JavaScript-трекер Saturnita Pulse.

В личном кабинете отображаются просмотры страниц, источники трафика, популярные URL, пользовательские события и UTM-кампании.

**Сценарий D — мониторинг API**

Разработчик добавляет:

`https://api.example.com/health`

или endpoint стороннего API, например погодного сервиса.

Система периодически отправляет запросы, измеряет задержку, записывает ошибки и показывает историю доступности.

**Сценарий E — автоматический мониторинг короткой ссылки**

Пользователь создаёт короткую ссылку на рекламную страницу и включает опцию «Мониторинг целевого URL».

Система проверяет работоспособность страницы независимо от пользовательских переходов. При недоступности отображает предупреждение в личном кабинете.

## 2. Технологический стек

### Backend

- Go — актуальная стабильная версия.
- Fiber — HTTP-framework.
- pgx / pgxpool — PostgreSQL driver и connection pool.
- PostgreSQL — основная база данных.
- golang-migrate — SQL-миграции.
- zerolog — структурированное логирование.
- godotenv — локальная загрузка `.env`.
- Go standard library — HTTP-клиент, контексты, конкурентность, криптография и вспомогательные функции.
- OpenAPI 3.x — спецификация публичного API.

**Не использовать GORM.** SQL-запросы должны быть явными; при необходимости допускается sqlc после обоснования.

### Frontend

- React + TypeScript.
- Vite.
- Tailwind CSS.
- shadcn/ui и Radix UI.
- React Router.
- TanStack Query.
- React Hook Form + Zod.
- Recharts — аналитические графики.
- Lucide React — иконки.
- Framer Motion / Motion — сдержанная анимация.
- date-fns — даты и интервалы.

Допускается изменение отдельных библиотек, если это улучшает проект, но не нужно без причины менять базовый стек.

### Infrastructure

- Docker, Docker Compose.
- Caddy — reverse proxy и HTTPS.
- PostgreSQL.
- Самостоятельный Go worker для проверок HTTP-ресурсов, запускаемый в том же приложении для MVP.
- GitHub Actions — CI.

Не добавлять Redis, Kafka, Kubernetes или брокер сообщений без доказанной необходимости.

## 3. Архитектура

Использовать **модульный монолит с разделением ответственности**.

Не создавать отдельные микросервисы для ссылок, аналитики, пользователей и мониторинга.

Рекомендуемая структура:

```text

│   │   ├── repository/
│   │   │   └── postgres/

│   │   ├── auth/
│   │   ├── links/
│   │   ├── domains/
│   │   ├── analytics/
│   │   ├── monitoring/
│   │   └── platform/
│   ├── migrations/
│   ├── tests/
│   ├── go.mod
│   └── Dockerfile
├── frontend/
│   ├── src/
│   │   ├── app/

│   │   ├── components/

│   │   ├── hooks/

│   │   ├── styles/

```

Структура ориентировочная. Не нужно дублировать одни и те же доменные сущности в нескольких пакетах.

### Архитектурные принципы

- HTTP handlers не содержат SQL и основной бизнес-логики.
- Service layer реализует сценарии использования.
- Repository layer отвечает за хранение данных.
- Доменные правила не зависят от Fiber.
- Все длительные операции поддерживают `context.Context`.
- Не использовать глобальное изменяемое состояние для бизнес-данных.
- У всех критичных операций должны быть понятные ошибки и корректные HTTP-статусы.
- Операции с несколькими связанными записями должны использовать транзакции.
- Предусмотреть graceful shutdown для HTTP-сервера и мониторингового worker.

# 4. Модуль авторизации

## Функциональность

Реализовать:

- Регистрацию по email и паролю.
- Вход и выход.
- Получение текущего профиля.
- Изменение имени и основных настроек.
- Смену пароля с подтверждением текущего.
- Защиту приватных маршрутов.
- Возможность завершить активную сессию.

### Требования безопасности

- Пароли хранить только в виде стойких хешей Argon2id или bcrypt.
- Использовать серверные сессии с криптографически случайными идентификаторами.
- Сессионные cookie: `HttpOnly`, `Secure` в production, подходящий `SameSite`.
- Предусмотреть CSRF-защиту для cookie-аутентификации.
- Ограничивать частоту запросов к авторизации.
- Никогда не хранить пароли и сессионные секреты в открытом виде в логах.
- Проверять права владения для всех приватных сущностей.

**Критерий готовности:** два зарегистрированных пользователя не могут читать или изменять ссылки, домены, сайты и мониторы друг друга.

# 5. Link Management

## 5.1. Создание короткой ссылки

Поля:

- Название ссылки.
- Исходный URL.
- Короткий идентификатор (slug).
- Домен короткой ссылки.
- Срок действия.
- Статус активности.
- Необязательные UTM-параметры.
- Включение мониторинга целевого URL.
- Необязательное ограничение количества переходов.

Slug может генерироваться автоматически либо задаваться пользователем.

Примеры:

`go.saturnita.ru/7Axd92`

`go.saturnita.ru/black-friday`

`alex.saturnita.ru/my-blog`

### Валидация

- Разрешать только допустимые схемы URL, по умолчанию `http` и `https`.
- Проверять максимальную длину URL и slug.
- Запрещать зарезервированные slug: `api`, `login`, `register`, `dashboard`, `admin`, `health` и другие системные маршруты на соответствующих доменах.
- Обеспечивать уникальность `(domain_id, slug)` на уровне БД.
- Разрешать одинаковые slug на разных доменах.
- Предотвращать циклические редиректы внутри Saturnita Pulse.

## 5.2. Перенаправление

При открытии короткого URL:

1. Определить хост.
2. Найти зарегистрированный домен.
3. Найти соответствующий slug.
4. Проверить активность и срок действия.
5. Проверить ограничение переходов.
6. Зафиксировать событие перехода.
7. Вернуть HTTP 302 с корректным `Location`.

Для обычного перехода использовать `302 Found`, чтобы не закреплять постоянный редирект в браузерном кеше.

Нельзя терять query-параметры исходного реферального URL.

Не включать автоматическое добавление пользовательских query-параметров к целевому URL без явного правила.

## 5.3. Управление ссылками

Пользователь должен иметь возможность:

- Просматривать список ссылок.
- Искать по названию, slug и исходному URL.
- Фильтровать активные и неактивные ссылки.
- Изменять название, исходный URL и статус.
- Копировать короткую ссылку.
- Просматривать аналитику.
- Включать и отключать мониторинг.
- Архивировать ссылку.
- Удалять ссылку с подтверждением.

Для MVP изменение slug после создания можно запретить, чтобы не ломать ранее опубликованные ссылки.

# 6. Domain Management

## 6.1. Системный домен

Основной сайт и dashboard размещаются на:

`saturnita.ru`

Короткие ссылки по умолчанию:

`go.saturnita.ru/{slug}`

На стадии локальной разработки допускаются отдельные localhost-адреса и тестовые домены.

## 6.2. Автоматические пользовательские поддомены

Реализовать регистрацию вида:

`{username}.saturnita.ru`

Пример:

`alex.saturnita.ru`

Пользователь вводит желаемое название. Backend проверяет доступность, допустимость и уникальность.

Если поддомен свободен — создаётся запись в PostgreSQL.

**Не создавать DNS-запись при каждой регистрации.**

Использовать предварительно настроенную wildcard DNS-запись:

`*.saturnita.ru → server IP`

Для HTTPS предусмотреть wildcard TLS-сертификат, получаемый через DNS-01.

Поддомены не должны конфликтовать с системными именами (`www`, `api`, `go`, `admin`, `mail` и т. д.).

## 6.3. Внешние пользовательские домены

Реализовать подключение домена клиента, например:

`go.company.ru`

Сценарий:

1. Пользователь вводит домен в личном кабинете.
2. Система создаёт заявку на подключение.
3. Показывает DNS-инструкцию: TXT для подтверждения владения и CNAME для маршрутизации.
4. Пользователь настраивает DNS.
5. Система проверяет владение.
6. Домен получает статус `verified`.
7. Reverse proxy обеспечивает HTTPS.
8. Домен становится доступен для новых коротких ссылок.

Предусмотреть состояния `pending`, `verified`, `active`, `error`.

Не считать наличие CNAME достаточным доказательством владения доменом.

Нельзя активировать произвольный чужой домен без подтверждения.

Если автоматическая выдача сертификатов для внешних доменов требует отдельного production-настроечного механизма, реализовать поддерживаемое решение через Caddy, документировать условия его работы и обеспечить защиту от злоупотребления выпуском сертификатов.

В локальной среде должен быть предусмотрен демонстрационный вариант без реального DNS.

# 7. Link Analytics

Собирать события при открытии коротких ссылок.

## 7.1. Данные перехода

- Идентификатор ссылки.
- Время перехода.
- Referer, если доступен.
- UTM source / medium / campaign.
- Категория устройства: desktop, mobile, tablet.
- Тип браузера.
- Операционная система при возможности.
- Страна при наличии подключённой GeoIP-базы.
- Признак предполагаемого бота.
- Идентификатор анонимной сессии, если используется.

Не хранить полный IP-адрес без необходимости. Не отправлять IP третьим лицам для геолокации по умолчанию.

## 7.2. Аналитическая панель

Для каждой ссылки показывать:

- Общее число переходов.
- Переходы за день, неделю, месяц.
- Динамику по датам.
- Приблизительное число уникальных посетителей/сессий.
- Распределение по устройствам.
- Источники переходов.
- UTM-кампании.
- Страны, если GeoIP доступен.
- Последние события.

Реализовать фильтры периода: 24 часа, 7 дней, 30 дней, произвольный диапазон.

### Графики

- Line chart — переходы по времени.
- Bar chart — источники трафика.
- Donut/Pie chart — устройства.
- Таблица — наиболее эффективные ссылки.

Для приблизительной уникальности явно указать метод расчёта. Не называть каждую анонимную сессию гарантированно уникальным человеком.

## 7.3. Общая аналитика

На главном Dashboard:

- Число активных ссылок.
- Число переходов за выбранный период.
- Наиболее популярные ссылки.
- Динамика переходов.
- Изменение к предыдущему аналогичному периоду.

# 8. Web Analytics

Разработать независимый механизм аналитики подключённых сайтов.

## 8.1. Регистрация сайта

Пользователь указывает:

- Название сайта.
- Домен.
- Часовой пояс.
- Статус аналитики.

Система выдаёт уникальный идентификатор сайта и JS-код подключения.

Например:

```html
<script
  defer
  src="https://saturnita.ru/tracker.js"
  data-site-id="PUBLIC_SITE_ID"
></script>
```

## 8.2. JavaScript Tracker

Tracker должен быть маленьким и не требовать React или других больших библиотек.

Функции:

- Сбор `pageview`.
- Отслеживание смены URL в SPA.
- Отправка пользовательских событий.
- Чтение UTM-параметров.
- Получение referer.
- Отправка событий с использованием `sendBeacon` или `fetch`.
- Исключение чувствительных query-параметров и личных данных из URL.

Пример API:

```javascript
window.Saturnita.track("signup_completed", {
  plan: "free",
});
```

Не собирать значения полей форм, содержимое страниц или персональные данные автоматически.

Не устанавливать tracking cookies по умолчанию.

Для privacy-friendly MVP использовать ограниченные анонимные события без кросс-сайтового отслеживания. Если позже появятся устойчивые идентификаторы пользователей, отдельно предусмотреть согласие, сроки хранения и необходимые настройки конфиденциальности.

## 8.3. Защита endpoint сбора

- Лимиты размера событий.
- Rate limiting.
- Проверка формата.
- Защита от SQL-инъекций.
- Проверка допустимых origins для сайтов, при этом учитывать, что `Origin` и site ID не являются секретами или полноценной аутентификацией.
- Устойчивость к случайным и массовым некорректным событиям.
- Не принимать произвольные вложенные payload без ограничений.

## 8.4. Дашборд веб-аналитики

Показывать:

- Pageviews.
- Анонимные сессии при поддержке их определения.
- Наиболее популярные страницы.
- Источники трафика.
- Устройства.
- Пользовательские события.
- UTM-кампании.
- Активность по датам.

Не реализовывать сложную систему рекламной атрибуции, fingerprinting или слежения за конкретными людьми.

# 9. Uptime Monitoring

Этот модуль должен поддерживать два сценария.

### Link Monitoring

Мониторинг целевого URL короткой ссылки.

### Endpoint Monitoring

Проверка произвольного разрешённого HTTP endpoint пользователя: собственного сайта, API или внешнего сервиса.

## 9.1. Создание монитора

Настройки:

- Название.
- URL.
- Тип: `link_target`, `website`, `api`.
- HTTP method: GET или HEAD для MVP.
- Интервал проверки.
- Timeout.
- Ожидаемый HTTP-статус или диапазон.
- Необязательное связанное `link_id`.
- Включён/выключен.
- Проверка конкретного значения JSON-поля — расширенная возможность.

Начальный интервал можно ограничить, например, минимумом в пять минут.

Не делать произвольные POST-запросы с пользовательскими телами к сторонним ресурсам в базовом MVP.

## 9.2. Go Monitoring Worker

Реализовать планировщик, который:

1. Находит мониторы, требующие проверки.
2. Распределяет задачи между ограниченным числом goroutine workers.
3. Выполняет безопасный HTTP-запрос.
4. Измеряет продолжительность.
5. Проверяет HTTP-ответ.
6. Сохраняет результат.
7. Определяет изменение состояния.
8. Планирует следующую проверку.

Предусмотреть обработку ошибок DNS, TLS, TCP, timeout и некорректных ответов.

Результат проверки должен содержать:

- `monitor_id`
- `checked_at`
- `http_status`
- `latency_ms`
- `success`
- `error_type`

## 9.3. Расчёт uptime

Для MVP использовать долю успешных проверок от общего количества проверок за выбранный период.

Отдельно пояснить в интерфейсе, что это **оценка доступности по периодическим проверкам**, а не точное непрерывное время работоспособности.

## 9.4. История сбоев

Показывать:

- Текущий статус.
- Последний успешный запрос.
- Время последней проверки.
- Длительность ответа.
- Историю проверок.
- Последовательности неудачных проверок.
- Процент успешных проверок.
- Среднюю и p95 latency.

Создать статусные состояния:

- Operational.
- Degraded.
- Down.
- Paused.
- Unknown.

Не считать единичную временную сетевую ошибку безусловным доказательством отказа стороннего сервиса.

## 9.5. Уведомления

Для первой рабочей версии:

Email/Telegram-уведомления можно реализовать после основной функциональности как дополнительный этап.

## 9.6. Безопасность мониторинга

Это критически важный пункт.

Необходимо защититься от SSRF:

- Запретить loopback, link-local, private и другие внутренние IP-диапазоны.
- Запретить cloud metadata endpoints.
- Проверять адрес после DNS-разрешения.
- Контролировать фактический IP, к которому устанавливается соединение.
- Проверять перенаправления повторно или полностью запрещать их для MVP.
- Не доверять одному лишь предварительному DNS lookup из-за DNS rebinding.
- Ограничивать число запросов, параллелизм, время выполнения и размер ответа.
- Не поддерживать произвольные нестандартные протоколы.
- Изолировать мониторинговый процесс от внутренней инфраструктуры, когда это возможно.

Не добавлять возможность отправлять секретные заголовки для внешних API до появления безопасного хранилища и понятной модели доступа.

# 10. База данных

Спроектировать нормализованную PostgreSQL-схему.

Предварительный перечень:

| Таблица          | Назначение                          |
| ---------------- | ----------------------------------- |
| `users`          | Пользователи                        |
| `sessions`       | Сессии                              |
| `domains`        | Пользовательские и системные домены |
| `links`          | Короткие ссылки                     |

| `sites`          | Сайты, подключённые к веб-аналитике |
| `web_events`     | События сайтов                      |
| `monitors`       | Настройки HTTP-мониторинга          |
| `monitor_checks` | История проверок                    |
| `incidents`      | Зафиксированные инциденты           |

Это базовая схема, а не требование использовать ровно десять таблиц.

При проектировании:

- Применять внешние ключи.
- Добавить индексы для частых фильтров и временных диапазонов.
- Учитывать многопользовательскую изоляцию.
- Использовать UTC для хранения временных меток.
- Предусмотреть политику хранения аналитических событий.
- Не использовать автоматическое создание схемы при запуске.
- Все изменения выполнять SQL-миграциями.

Кодовые идентификаторы ссылок и регистрация поддоменов должны иметь ограничения уникальности непосредственно в PostgreSQL.

Для курсовой подготовить ER-диаграмму.
